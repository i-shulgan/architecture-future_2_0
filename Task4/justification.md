# Обоснование конфигурации

Конфигурация разворачивает **шаблон доменной среды** — работу 0.5 [роадмапа](../Task3/roadmap.md). Это минимальный, но полноценный срез целевой архитектуры:

- **Сеть с тремя зонами** разного уровня доверия: публичная зона администрирования, платформа данных и медицинский контур.
- **Исходящий интернет через NAT-шлюз** без публичных адресов у рабочих ВМ.
- **Компонент платформы данных** — каталог Iceberg-таблиц Nessie.
- **Компонент медицинского контура** — ВМ адаптера событий клиник.
- **Бакет Object Storage** под Lakehouse, зашифрованный ключом KMS.

Новый домен или партнёр разворачивается тем же кодом: в `terraform.tfvars` добавляются записи в `subnets`, `security_groups` и `vms`.

## 1. Состав ресурсов

| Ресурс | Количество | Назначение |
|---|---|---|
| `yandex_vpc_network` | 1 | Сеть доменной среды |
| `yandex_vpc_subnet` | 3 | `public` — bastion; `platform` — платформа данных; `clinic` — медицинский контур |
| `yandex_vpc_gateway` (shared egress) | 1 | NAT-шлюз для исходящего трафика приватных подсетей |
| `yandex_vpc_route_table` | 1 | Маршрут `0.0.0.0/0` → NAT-шлюз, привязан к приватным подсетям |
| `yandex_vpc_security_group` | 3 | Правила доступа для bastion, платформы и медицинского контура |
| `yandex_compute_instance` | 3 | `bastion`, `nessie`, `clinic-adapter` |
| `yandex_compute_disk` | 2 | Отдельные диски данных для `nessie` и `clinic-adapter` |
| `yandex_kms_symmetric_key` | 1 | Ключ шифрования бакета Lakehouse с ежегодной ротацией |
| `yandex_storage_bucket` | 1 | Бакет Lakehouse с шифрованием на стороне сервера (SSE-KMS) |

Ресурсов всего 16. Также используются два data source:

- `yandex_compute_image` — актуальный образ Ubuntu 22.04 LTS по семейству, без жёстко прописанного ID;
- `yandex_client_config` — ID каталога для имени бакета.

## 2. Размеры виртуальных машин

Все ВМ используют платформу `standard-v3` (Intel Ice Lake). Это актуальное поколение с минимальной ценой за vCPU, на нём доступны уровни производительности 20 % и 50 %. Размеры выбраны по реальной нагрузке роли и по допустимым сочетаниям для платформы: при доле ядра 20 % и 50 % — 2 или 4 vCPU и от 0,5 до 4 ГБ RAM на vCPU.

| ВМ | vCPU / доля ядра | RAM | Почему так |
|---|---|---|---|
| `bastion` | 2 / 20 % | 1 ГБ | Единственная задача — проксировать SSH-сессии администраторов. Нагрузка эпизодическая, гарантированная доля 20 % и минимальная память достаточны |
| `nessie` | 2 / 50 % | 4 ГБ | Nessie — Java-сервис на Quarkus. JVM нужны 1,5–2 ГБ heap, плюс Docker и кэш ОС. Каталог обслуживает каждый запрос SQL-движка к метаданным таблиц, поэтому гарантированная доля поднята до 50 %: задержка каталога напрямую влияет на скорость отчётов |
| `clinic-adapter` | 2 / 20 % | 2 ГБ | Java-адаптер публикует события счетов. Поток событий небольшой и равномерный, 2 ГБ хватает на JVM и буфер outbox |

Масштабирование — изменение `cores`, `memory` и `core_fraction` в `terraform.tfvars`. Terraform применит его на месте, без пересоздания ВМ (`allow_stopping_for_update`). ВМ при этом останавливается на время изменения, поэтому для продуктива такие изменения планируются в окно обслуживания.

## 3. Диски

| Диск | Тип | Размер | Почему так |
|---|---|---|---|
| Загрузочный `bastion` | `network-hdd` | 10 ГБ | Только ОС и SSH, скорость диска не важна. Размер покрывает образ Ubuntu с запасом под обновления |
| Загрузочный `nessie` | `network-hdd` | 20 ГБ | ОС, Docker и образ Nessie. Диск читается при старте сервиса, в работе каталога он не участвует, поэтому HDD достаточно |
| Загрузочный `clinic-adapter` | `network-hdd` | 15 ГБ | ОС, OpenJDK и приложение адаптера |
| Данные `nessie` | `network-ssd` | 20 ГБ | Хранилище версий каталога (RocksDB) на `/data`. RocksDB выполняет много мелких случайных чтений и записей, а каталог обслуживает каждый запрос SQL-движка к метаданным. SSD держит задержку каталога низкой, от неё зависит скорость отчётов. Объём небольшой: метаданные Iceberg занимают мало места, сами данные таблиц лежат в Object Storage |
| Данные `clinic-adapter` | `network-hdd` | 10 ГБ | Буфер outbox на `/data`: события не теряются, если журнал событий временно недоступен |

Данные вынесены на **отдельные диски** (`yandex_compute_disk` + `secondary_disk`):

- их жизненный цикл не зависит от ВМ: при пересоздании ВМ с новым образом данные сохраняются;
- их можно увеличить отдельно от системного диска;
- у них отдельные снапшоты.

Разметку и монтирование выполняет cloud-init по имени устройства `/dev/disk/by-id/virtio-data`. Имя задаётся в Terraform через `device_name = "data"`.

## 4. NAT и сетевая изоляция

В Yandex Cloud исходящий интернет для ВМ можно дать двумя способами:

1. **Публичный IP на интерфейсе** (`nat = true`) — каждая ВМ получает внешний адрес и становится доступна из интернета, если это разрешают правила.
2. **NAT-шлюз** (`yandex_vpc_gateway` с `shared_egress_gateway`) и таблица маршрутов на приватных подсетях — у ВМ нет внешних адресов, исходящий трафик идёт через шлюз, входящие соединения из интернета невозможны.

Выбран **NAT-шлюз** для подсетей `platform` и `clinic`, публичный IP — только у `bastion`.

| Причина | Пояснение |
|---|---|
| Безопасность медицинских и финансовых данных | Сервисы медицинского контура и платформы данных недоступны из интернета на сетевом уровне, а не только по правилам групп безопасности. Это одна из мер защиты персональных и медицинских данных в [целевой архитектуре](../Task1/README.md) |
| ВМ по-прежнему получают обновления | Пакеты ОС, OpenJDK и Docker-образ Nessie скачиваются через шлюз |
| Единая точка администрирования | Администраторы попадают на внутренние ВМ только через bastion (`ssh -J`). Bastion пускает SSH только из `admin_cidrs` и только по ключу |
| Экономия | Один публичный адрес вместо трёх. Шлюз общий для всех приватных подсетей, новые домены пользуются им без дополнительных адресов |

Группы безопасности дополняют изоляцию:

- платформа принимает SSH только с bastion, а запросы к API Nessie — только из своей подсети и с bastion (администраторы ходят к API через SSH-туннель);
- источник SSH для внутренних ВМ — фиксированный внутренний адрес bastion `10.10.0.10/32` (`from_vms`), а не вся подсеть `public`. Если в публичной подсети появится другая ВМ, доступа к внутренним ВМ у неё не будет. В текущей структуре все группы создаются одним ресурсом с `for_each`, и ссылка из их правил на группу безопасности bastion образует цикл зависимостей. Обойти его можно отдельными ресурсами правил (`yandex_vpc_security_group_rule`) или отдельным ресурсом для группы bastion, но это усложняет шаблон, поэтому выбран фиксированный адрес;
- правило доступа к API Nessie Terraform добавляет сам в группу безопасности ВМ с ролью `nessie`. Порт задаётся один раз в `nessie_port` и используется и в правиле, и в запуске контейнера, поэтому разойтись они не могут;
- медицинский контур принимает только SSH с bastion и трафик изнутри контура. **Входящие соединения из платформы данных в медицинский контур запрещены.** В целевой архитектуре это обеспечивается ещё и отдельным облаком, см. ниже;
- исходящий трафик медицинского контура тоже ограничен: внутри контура (включая DNS подсети), HTTP и HTTPS для обновлений ОС и пакетов через NAT-шлюз и синхронизация времени. Соединение из медконтура в платформу данных невозможно: группа безопасности платформы не принимает трафик из подсети `clinic`, а других открытых портов у медконтура нет. Так данные не могут уйти из контура по произвольному протоколу. Когда в среде появится журнал событий, адаптеру добавляется одно правило в `terraform.tfvars`: TCP 9091 к подсети Kafka;
- для bastion и платформы `egress` не задан, у них остаётся правило по умолчанию: весь исходящий трафик.

**Тестовая среда и целевые контуры.** В целевой архитектуре медицинский контур — отдельное облако. Единственный путь из платформы данных к нему — CDC-трансфер через read-only endpoint. Тестовая среда разворачивается в одном каталоге, поэтому изоляция показана подсетью и группой безопасности. В landing zone (работа 0.5 роадмапа) тот же код применяется отдельно к облаку медицинского контура, облаку банка и облаку платформы, каждый раз со своим `terraform.tfvars`. CDC-трансфер в тестовую среду не входит.

В `terraform.tfvars` в `admin_cidrs` стоит заглушка из документационного диапазона `203.0.113.10/32`. Реальный адрес администратора задаётся в локальном файле `admin.auto.tfvars`: он исключён из Git и переопределяет значение из `terraform.tfvars`. Так адреса сотрудников не попадают в репозиторий, а SSH на bastion открыт только с конкретного адреса. Для продуктива в файле переменных среды указывается диапазон корпоративного VPN.

## 5. Прерываемые ВМ и стоимость

Все ВМ тестовой среды прерываемые (`preemptible = true`): они в несколько раз дешевле обычных и подходят для проверки развёртывания. В продуктиве флаг выключается для `nessie` и `clinic-adapter`, это одна строка в `terraform.tfvars`.

Тестовая среда проверяет развёртывание, сетевую схему и настройку ВМ, но не отказоустойчивость: Nessie работает на одной ВМ в одной зоне, а RocksDB на её диске — единая точка отказа. В продуктиве каталог разворачивается иначе:

- хранилище версий — JDBC на Managed PostgreSQL с хостами в трёх зонах доступности вместо RocksDB на диске ВМ;
- несколько реплик Nessie без состояния в группе ВМ (`yandex_compute_instance_group`) в разных зонах;
- внутренний сетевой балансировщик перед репликами, Trino и пайплайны обращаются к его адресу.

Выход из строя ВМ или зоны тогда не останавливает отчёты. Изменения кода — новые ресурсы в том же шаблоне, логика сети и групп безопасности остаётся прежней.

Бакет Lakehouse:

- ограничен 10 ГБ (`max_size`);
- закрыт для анонимного доступа;
- шифруется на стороне сервера ключом KMS (SSE-KMS). Это мера защиты ПДн для контура платформы: даже при ошибке в правах доступа к бакету объекты без доступа к ключу не прочитать. Ключ ротируется раз в год (`kms_rotation_period`), старые версии ключа остаются для чтения ранее записанных объектов;
- создаётся с `force_destroy = true`, чтобы `terraform destroy` полностью убирал тестовую среду. В продуктиве флаг выключается, а у ключа включается защита от удаления (`deletion_protection`).

## 6. Почему декларативный подход

Terraform описывает **желаемое состояние** инфраструктуры, а не последовательность команд. Порядок действий Terraform строит сам по графу зависимостей: сеть → шлюз и таблица маршрутов → подсети → группы безопасности и диски → ВМ; ключ KMS → бакет.

| Свойство | Что даёт |
|---|---|
| Идемпотентность | Повторный `terraform apply` без изменений в коде ничего не меняет. Скрипт не нужно защищать от повторного запуска |
| Предсказуемость | `terraform plan` показывает, что будет создано, изменено или удалено, до любых действий в облаке. План проходит ревью так же, как код |
| Обнаружение дрейфа | Ручные изменения в консоли видны в следующем плане и откатываются к описанному состоянию |
| Меньше ошибок | Зависимости и порядок создания вычисляются автоматически. Нет риска создать ВМ раньше подсети или забыть привязать таблицу маршрутов |
| Удаление без остатков | `terraform destroy` удаляет ровно то, что создано по этому коду |

Императивный скрипт (последовательность вызовов `yc`) пришлось бы дополнять проверками, ветвлениями и откатом. И всё равно он не показал бы разницу между текущим и нужным состоянием.

## 7. Как IaC обеспечивает воспроизводимость и масштабируемость

**Воспроизводимость:**

- **Код в Git.** Вся конфигурация хранится в репозитории: у каждого изменения есть автор, ревью и история, откат — это возврат к предыдущему коммиту и `apply`.
- **Одна логика для всех сред.** `main.tf` не содержит значений конкретной среды. dev, stage и prod отличаются только файлом переменных. Каталог и облако берутся из окружения, поэтому тот же код разворачивается в другом каталоге без правок.
- **Однотипные ВМ.** Образ ОС берётся по семейству при создании ВМ. Выход нового образа не пересоздаёт работающие ВМ (`lifecycle.ignore_changes`), обновление образа — осознанное действие через `terraform apply -replace`. Настройка ВМ (пользователь, ключи, диски, Docker, Nessie, OpenJDK) выполняется cloud-init из шаблона, который передаёт Terraform. На уровне инфраструктуры ручных шагов внутри ВМ нет. Выкладка кода приложений — отдельный процесс поставки.
- **Явные версии.** Провайдер зафиксирован: `~> 0.235` и `.terraform.lock.hcl` с хэшами для macOS, Linux и Windows. Образ Nessie зафиксирован по версии (`nessie_image`). Одинаковый код даёт одинаковый результат у всех участников команды.
- **Состояние отделено от кода.** `terraform.tfstate` не попадает в Git. В продуктиве state хранится в бакете Object Storage с блокировкой — тогда несколько администраторов работают с одной средой без конфликтов.

**Масштабируемость:**

- **Новая подсеть, группа безопасности или ВМ** — запись в `subnets`, `security_groups` или `vms`, ресурсы создаются через `for_each`. `main.tf` при этом не меняется. Например, среда домена «Финтех» добавляется тремя блоками в `terraform.tfvars`:

  ```hcl
  subnets         = { ..., fintech = { zone = "ru-central1-b", cidr = "10.10.30.0/24", private = true } }
  security_groups = { ..., fintech = { description = "Финтех", ingress = [
    { description = "SSH с bastion", protocol = "TCP", port = 22, from_vms = ["bastion"] } ] } }
  vms             = { ..., fintech-app = { subnet = "fintech", security_group = "fintech", role = "service", ... } }
  ```
- **Новый домен или партнёр** — тот же код с другим файлом переменных в своём каталоге. Это и есть шаблон доменной среды, на котором в роадмапе построено подключение фармкомпаний и производителя оборудования за недели.
- **Вертикальное масштабирование** — изменение `cores`, `memory` и `core_fraction`. **Горизонтальное** — новые элементы `vms`. **Зональное** — подсети в других зонах доступности: значение `zone` у подсети.
- **Защита от ошибок.** Входные данные проверяются: `validation` для ролей ВМ и ссылок на подсети, `precondition` для ссылок на ВМ в правилах групп безопасности. План показывает влияние каждого изменения до применения.

## 8. Что делается вручную

Полная схема — на [диаграмме автоматизации развёртывания](diagram.png).

| Что | Почему вручную |
|---|---|
| Организация, платёжный аккаунт, облако, каталог | Создаются один раз и требуют прав владельца. Это граница, внутри которой работает Terraform |
| Учётная запись или сервисный аккаунт с ролями `editor`, `storage.admin` (настройка доступа и размера бакета) и `kms.keys.encrypterDecrypter` (шифрование бакета ключом KMS), выпуск токена или ключа | Секреты не хранятся в коде, передаются через переменные окружения |
| SSH-ключ администратора | Личный секрет администратора, в конфигурацию попадает только публичный ключ |
| Выкладка кода адаптера событий | Это цикл поставки приложения (CI/CD), а не инфраструктуры |
| Адрес администратора в `admin_cidrs` — локальный файл `admin.auto.tfvars` | Адреса сотрудников не хранятся в репозитории; для продуктива — диапазон корпоративного VPN |
